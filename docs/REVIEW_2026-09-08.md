# Pre-release resource and provider review — 2026-09-08

The host was already collecting metrics every 60 seconds, but they were difficult to discover. Overview now shows each machine's CPU, RAM, swap and disks with usage bars and readable capacities. Recent charts provide 1/6/24-hour windows, preserved peaks, gaps, thresholds and keyboard/pointer inspection. Secondary counters remain available without pushing the main charts far down the page. Collection remains optional per machine; threshold alerts and charts need no LLM. Compressed history and daily summaries are retained.

The real connection is direct **llama.cpp at `http://127.0.0.1:8081/v1`**, with Qwen3-8B. BigPAPI occupies port 8080 and returns HTML at `/v1/models`; it is not the model API. The user's balancer URL remains to be identified. No working endpoint or remote transmission preference was changed. Provider presets now cover Ollama, llama.cpp, LM Studio, vLLM, LiteLLM and compatible balancers/custom servers. One model endpoint is active at a time.

Connection discovery and diagnostics now use the actual form before saving. Switching servers no longer implicitly reuses the old API key. Draft tests preserve the active configuration and its verification state. Metadata discovery respects remote-transmission permission, allows selection when the previous Ollama model is missing, and bounds Ollama context suggestions by its running window. Ollama's reasoning flag is now sent through its native `think` parameter. Malformed provider responses produce a diagnostic error. Server-specific reasoning settings are preserved when revisiting setup for an unchanged endpoint.

The measurement/persistence microbenchmark ran as UID 1000: median 12.3 ms wall / 2.9 ms CPU per sample, compressed payload around 330 bytes, with no permission errors. This excludes the rest of the portal, alert handling and SQLite indexes/rollups. See [metric cost and permissions](METRICS.md).

The running observer had continuous capture, periodic analysis every 300 seconds, no failed jobs and no consecutive failed cycles. Its last-hour sample showed **3,524 arrivals, 379 covered events, 2,992 marked capacity**, approximately **59 arrivals/minute versus 6 covered/minute**. Other events were still pending in that rolling window. Of those arrivals, 2,762 belonged to service `python`; the model calls averaged about 58 seconds. These counters describe the measured window, not a detection benchmark or a guarantee about the next hour.

The main remaining release limitation is coverage and detection quality under that input volume. Preview structured-priority and narrowly scoped repetition filters before enabling them, compare representative models or proxy routes using a labelled corpus, and report coverage alongside throughput. No filters were silently enabled. Log originals and existing findings were preserved.

Other follow-ups: live compatibility checks with the actual balancer and other installed servers; multi-provider saved profiles or per-machine routing if needed; cgroup-specific metrics for containers, network throughput and disk I/O rates; long-term trend calibration and a real Omarchy desktop test. The current resource collector is for Linux hosts and does not infer another computer's CPU/RAM from imported logs.

Validation: **300 Python tests passed**, plus **six Chromium journeys** (portal, setup, problem investigation, metrics, themes and provider configuration). The provider journey covers discovery and synthetic testing without changing the active server, secret isolation, reasoning preservation when reopening setup, English/Spanish and mobile layout. The metric journey starts on Overview and checks optional activation, GiB totals, a non-root disk, keyboard chart inspection and separate LLM usage. All five themes passed contrast/layout checks. Wheel packaging succeeded and `pip check` found no broken requirements. Two TestClient dependency deprecation warnings remain.
